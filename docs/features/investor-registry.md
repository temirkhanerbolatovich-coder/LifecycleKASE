# Investor Registry: governed profiles and local-demo review

Administrator and Auditor can read `GET /api/v1/investors?limit=20&cursor=<uuid>&search=<query>`. Pages default to 20 and are capped at 100 investors, ordered by creation time/id; the extra row determines `nextCursor`. Search is applied on the server before pagination: display name and external reference use case-insensitive matching, wallet addresses retain case-sensitive matching, and a complete UUID also matches Investor ID. The trimmed query is limited to 200 characters without control characters. Each investor includes its `registryVersion`, a wallet count and at most 20 wallet previews with their own `registryVersion`.

`GET /api/v1/investors/:id` retrieves a profile independently of the loaded list. `GET /api/v1/investors/:id/wallets?limit=20&cursor=<walletUuid>` pages all wallets, including pending, blocked and revoked records, in wallet-ID order with the same 20/100 limits and `{ items, nextCursor }` response. A wallet cursor must belong to that investor. Operator wallets are outside this mapping. The workspace opens a selected record through `#investors?selected=<uuid>`, restores it through the detail endpoint and offers continuation pages for its complete wallet history. Search changes reset list pagination; status/sort controls apply to the displayed search results.

Administrator alone can call:

- `POST /api/v1/investors`: `displayName` (1–200 characters), `type` (`INDIVIDUAL`/`INSTITUTIONAL`), two-letter `countryCode`, optional unique `externalReference` (1–100 characters).
- `POST /api/v1/investors/:id/profile`: the complete `displayName`, `type`, `countryCode`, `externalReference` profile plus current `expectedVersion` and fixed `reasonCode`. Use explicit `null` to clear the reference; omitted fields are invalid.
- `POST /api/v1/investors/:id/wallets`: `address`, a valid Solana public key. Network is fixed to `SOLANA_LOCALNET` in this local slice.
- `POST /api/v1/investors/:id/eligibility`: make the single local-demo decision `ELIGIBLE`/`DEMO_CRITERIA_MET` or `NOT_ELIGIBLE`/`DEMO_CRITERIA_NOT_MET`.
- `POST /api/v1/investors/:id/eligibility/review`: change an existing decision to `ELIGIBLE`, `NOT_ELIGIBLE` or `SUSPENDED`, with the investor's current `expectedVersion` and an allowed `reasonCode`.
- `POST /api/v1/investors/:id/wallets/:walletId/status`: temporarily change a verified investor wallet from `ACTIVE` to `BLOCKED`, or from `BLOCKED` to `ACTIVE`, with that wallet's current `expectedVersion` and an allowed `reasonCode`.
- `POST /api/v1/investors/:id/wallets/:walletId/revoke`: terminally revoke an investor wallet with one fixed reason code: `OWNER_REQUEST`, `SECURITY_CONCERN`, `WALLET_REPLACEMENT` or `REGISTRY_CORRECTION`.
- `POST /api/v1/investors/:id/wallets/:walletId/verification/challenge`: create a short-lived, administrator-bound ownership message for a pending localnet wallet.
- `POST /api/v1/investors/:id/wallets/:walletId/verification/verify`: submit the exact nonce and Ed25519 message signature to activate that wallet.

Unknown fields, malformed identifiers, unsupported enums and control characters are rejected server-side. New investors use `NOT_STARTED` KYC and `PENDING_REVIEW` eligibility. An unreviewed investor record can have lifecycle status `ACTIVE`, but this is not payout eligibility. Attached wallets begin `PENDING` with null verification/revocation times and become `ACTIVE` only after ownership proof. Existing wallet ownership, including operator wallets, cannot be reassigned. Missing/inactive investors fail closed. No real KYC, private keys or personal documents may be supplied; use synthetic demo labels and references only.

The initial eligibility decision is a one-time transition from `PENDING_REVIEW` to `ELIGIBLE` or `NOT_ELIGIBLE`. Approval requires at least one active, verified, non-revoked wallet. The database stores a fixed non-PII reason code and review timestamp; the same Serializable transaction appends `INVESTOR_ELIGIBILITY_DECIDED` with actor/correlation evidence. This is a synthetic local-demo decision, not KYC/AML or a legal eligibility opinion.

## Profile correction

Profile correction uses the creation field limits, validates country code as two raw ASCII letters before uppercasing and requires one of `REGISTRY_CORRECTION`, `PERIODIC_REVIEW`, `SECURITY_CONCERN` or `OWNER_REQUEST`. Unicode case expansion is not accepted as country input. The API rejects unknown fields, stale versions, duplicate references, unchanged profiles and edits to a `CLOSED` investor. Correction of an `ACTIVE` or `SUSPENDED` profile preserves stable Investor ID, lifecycle/KYC/eligibility decisions, wallet ownership/proof and captured obligations. It does not restore a suspended investor or create eligibility.

The capture-window lock, compare-and-set and Serializable actor audit apply to the complete update. `INVESTOR_PROFILE_UPDATED` records changed field names, reason, previous/new version, actor and correlation; it excludes previous/new profile values. Audit failure rolls back the update. Existing migration 20 already versions profile facts, so this continuation adds no migration or on-chain instruction. [ADR-028](../decisions/ADR-028-registry-review-versioning.md) remains the governing version/audit decision. Current validation and publication boundaries are recorded in [profile continuation](../testing/registry-profiles-2026-10-11.md).

Later correction, suspension or restoration uses the separate `/eligibility/review` route. It requires an `ACTIVE` investor whose eligibility has already been decided, rejects repeated decisions and requires an active verified non-revoked wallet when restoring `ELIGIBLE`. The allowed operator reasons are `REGISTRY_CORRECTION`, `PERIODIC_REVIEW`, `SECURITY_CONCERN` and `OWNER_REQUEST`; arbitrary text is rejected. The audit event `INVESTOR_ELIGIBILITY_REVIEWED` retains the previous/new eligibility, previous/new version and operator reason. The stored domain reason remains `DEMO_CRITERIA_MET`, `DEMO_CRITERIA_NOT_MET` or `DEMO_ELIGIBILITY_SUSPENDED`, so existing payout rules keep their established explicit demo contract. Eligibility suspension does not change `Investor.status`, KYC, token ownership or historical calculations.

Temporary wallet blocking uses the same four operator reasons and appends `INVESTOR_WALLET_STATUS_CHANGED`. It requires an active investor and a verified, non-revoked investor wallet already in `ACTIVE` or `BLOCKED`; pending, revoked and operator-bound wallets cannot use this transition. Blocking preserves the wallet address, investor mapping, original `verifiedAt` and revocation evidence. Unblocking restores only current wallet availability. It does not restore terminal revocation, alter a saved receiver, transfer tokens or rewrite a signed attempt.

Every record-changing mutation inserts an actor/correlation-linked audit event in the same Serializable Prisma transaction as the state change. Unique/reference and concurrent transaction conflicts return 409; audit failure aborts the transaction. Audit metadata omits display names, country data and wallet addresses. Existing database migration guards make stored audit rows immutable. PostgreSQL uniqueness is authoritative, not the preliminary address lookup.

Wallet ownership verification requires two independent conditions: an active Administrator session authorizes the mutation, and the exact pending wallet signs a domain/origin/investor/wallet/nonce/expiry-bound message. It is not a Solana transaction. If Phantom exposes multiple accounts under the same profile, operator login explicitly selects the registered operator address and ownership proof separately resolves the exact pending address; the shared Phantom profile name has no authorization meaning. The challenge is purpose-separated from operator login, bound to the requesting Administrator and consumed atomically with `PENDING → ACTIVE`, `verifiedAt` and `INVESTOR_WALLET_OWNERSHIP_VERIFIED` audit persistence. Invalid, expired, replayed or altered proofs fail closed. Verification does not change KYC or eligibility and does not authorize payments.

Wallet revocation is a terminal `PENDING|ACTIVE|BLOCKED → REVOKED` transition. It records `revokedAt`, a fixed non-PII reason and `INVESTOR_WALLET_REVOKED` in one Serializable transaction; repeating it returns a conflict. It applies only to a wallet already mapped to the route investor, so it cannot revoke an operator wallet or reassign ownership. Revocation does not silently overwrite the investor's eligibility decision. Snapshot capture may still record a revoked or blocked holder balance for supply reconciliation and historical entitlement evidence. Existing [coupon](coupon-execution-and-receipts.md) and [redemption](redemption-execution-and-receipts.md) preparation gates reject a selected receiver that is currently blocked, revoked or ineligible. Later registry changes cannot erase finalized chain evidence or undo a previously signed transaction; confirmation/recovery retains the original committed terms and signature. Isolated settlement acceptance and retained-owner/public-network acceptance remain separate.

## Versions and snapshot protection

Profile/review/status writes require a positive integer `expectedVersion` below the PostgreSQL integer maximum. It is the investor version for profile correction or eligibility review and the wallet version for temporary status changes. A stale version returns `409 REGISTRY_CONFLICT`; reload the affected record and review its current state before submitting a new decision. An unchanged profile or repeated/unsupported transition returns `REGISTRY_TRANSITION_INVALID` or `WALLET_STATUS_TRANSITION_INVALID`. Missing/inactive records and invalid input retain their existing 404/409/400 contracts. These are explicit requests, not idempotency keys.

Migration `20261011130000_registry_review_versions` adds positive `registry_version` columns defaulting to 1 and database triggers that advance the version for every effective investor/profile/eligibility/KYC or wallet/mapping/status/verification change. This includes controlled direct SQL writes. The triggers assign `OLD + 1` even when the API requests an increment; changing a version alone is rejected. A round trip such as `ACTIVE → BLOCKED → ACTIVE` therefore invalidates an older form and snapshot candidate despite the restored status. The trigger does not authorize direct SQL or replace the API's atomic actor audit. See [ADR-028](../decisions/ADR-028-registry-review-versioning.md).

Snapshot preparation retains transient `registryFacts` for each captured wallet: identity/mapping, network/status, exact verification/revocation timestamps, raw investor eligibility/lifecycle and both registry versions. Persistence checks those facts again before creating any snapshot rows. Changed facts return `REGISTRY_CHANGED`; missing or inconsistent candidate facts return `CANDIDATE_CHANGED`. These facts do not enter canonical snapshot-v2 JSON, stored snapshot rows, receipt bytes or PDA derivation. An already persisted pending snapshot resumes from its original commitment.

At capture, an active investor keeps its stored eligibility; lifecycle `SUSPENDED` becomes snapshot eligibility `SUSPENDED`, and `CLOSED` becomes `NOT_ELIGIBLE`. Restoring that investor later cannot grant eligibility at the earlier captured point. Conversely, suspending a currently eligible investor or blocking its selected wallet prevents future unsigned execution without rewriting a previously captured eligible snapshot or approved obligation. Current eligibility and immutable record-point eligibility are independent checks.

Profile correction, wallet attachment, wallet-ownership challenge/activation, revocation, initial eligibility decisions, later eligibility review and temporary wallet status changes are blocked while any `SCHEDULED` action in this single demo workspace is inside its configured inclusive snapshot capture window (`record_at` through `SNAPSHOT_GRACE_SECONDS`, maximum 300 seconds). The API returns `409 REGISTRY_CAPTURE_LOCKED`. This deliberately broad lock avoids changing mutable registry facts while the effective snapshot is being formed. It is not a scalable multi-issuer lock; issuer-scoped locking or append-only effective-time history is required later. Database version triggers detect stale facts from controlled non-HTTP writes, but do not provide historical ownership reconstruction.

Routes require enabled authentication and an unexpired operator session. Writes additionally require an exact allowed Origin and the existing per-client mutation limiter, returning 429/Retry-After on limit. Reads are Administrator/Auditor only; responses use `no-store`. The fixed Next.js same-origin proxy exposes only the implemented route paths. No token-auth bypass or automatic role provisioning is added.

## Local usage

Start Docker/PostgreSQL and apply migrations using the [README](../../README.md). Configure `AUTH_ENABLED=true`, `AUTH_DOMAIN=localhost:3000`, `AUTH_ALLOWED_ORIGINS=http://localhost:3000` for the local environment and provision an authorized local operator through the [controlled runbook](../operations/operator-provisioning.md). Never overwrite an existing `.env` containing user configuration. Start API/web, sign into `/dashboard`, then follow the registry workflow. Auditor sees only the list and evidence; Administrator sees creation, ownership, eligibility review and applicable block/unblock controls. The UI shows the active Phantom address and enables ownership confirmation only when it exactly matches the pending wallet.

For profile correction, review or block/unblock, select an explicit reason and confirm the displayed record/version. Successful writes require a newer read of the affected record before another change is enabled. A failed follow-up read is reported as saved-but-refresh-failed, retains the refresh lock and does not replay the POST. The controls and notices support RU/EN; QA mode simulates these requests in page-local state. Failed writes retain the form inputs; language changes preserve entered values. A profile draft keeps its original version: if a newer record arrives, explicitly replace the stale draft before editing the newer facts. Search/detail reads cancel superseded requests while preserving the shared 15-second timeout. Use unique demo references to identify a create request after a lost response; refresh before retrying. There is no idempotency-key contract yet; a duplicate reference/address is a conflict, not a second successful creation.

## Testing and limits

Run `npm run test --workspace @lifecycle-kase/api` and `npm run check` for unit, schema and type checks. Run `npm run test:registry:database` with Docker PostgreSQL available for real HTTP/PostgreSQL acceptance. The runner does not load `.env`: it defaults to the local development database on port 55432, or accepts `REGISTRY_TEST_DATABASE_URL` (and the CI-provided `DATABASE_URL`) only when it identifies the `lifecycle_kase` database on an explicit loopback port. The database user needs CREATE DATABASE permission. It creates a uniquely named disposable database, deploys migrations, starts an ephemeral API and signs login messages using synthetic in-memory keys. It drops only its own database in cleanup; normal local records are untouched.

The registry runner covers role/session/Origin boundaries, investor and pending-wallet creation, exact Ed25519 ownership proof and replay rejection, initial and corrected/suspended/restored eligibility, temporary block/unblock, terminal revocation, optimistic concurrency including round-trip status changes, reason/time/audit, snapshot-window mutation locking, duplicate and concurrent-reference conflicts, transaction rollback on audit failure, immutable audit rows, network/status guards, cursor pagination, rate limits and logout. Its governance helper also checks that registry changes leave a synthetic captured snapshot and approved calculation unchanged while current receiver gates respond to the new state. Snapshot unit tests cover stale lifecycle/version/verification/revocation facts and persistence without changing canonical-v2. These checks do not execute chain settlement; fresh counts and actual acceptance results belong in dated testing reports.

The profile helper adds real HTTP/PostgreSQL coverage for independent detail, wallet history beyond 20 previews, investor-bound cursors and server search before pagination. Profile cases cover strict full fields/reasons, clearing a reference, no-op/stale/concurrent writes, unique-reference conflicts, capture lock, closed/suspended boundaries, audit-value privacy/rollback and preservation of synthetic snapshot/calculation/settlement evidence. The [profile continuation](../testing/registry-profiles-2026-10-11.md) records actual results; browser form behavior is a separate acceptance layer.

Migration `20261001112000_localnet_wallet_registry` permits localnet alongside Devnet in the wallet network guard while preserving ACTIVE/REVOKED timestamp requirements and excluding mainnet. Instrument and settlement-asset network guards remain unchanged. Local Compose binds PostgreSQL only to IPv4/IPv6 loopback; set `API_LISTEN_HOST=127.0.0.1` for local API use. The API defaults to `0.0.0.0` when unset to preserve hosting compatibility.

The owner confirmed the real local two-account Phantom flow at `http://localhost:3000/dashboard` on 2026-10-01: operator login/session with Account 1, investor creation, Account 2 attachment, account-switch detection, exact ownership signing and resulting active wallet presentation. On 2026-10-02 the owner also confirmed Account 2 terminal revocation and the Account 3 Auditor presentation: the Auditor can see the registry and revocation evidence but has no create, mapping, verification, eligibility or revocation controls. Extension recovery is not yet manually accepted; automatic HTTP coverage does not substitute for that check.

This slice does not implement `Investor.status` lifecycle administration/suspension/closure, registry exports or issuer-scoped multi-tenant access. Lifecycle closure requires a separate holdings/live-action/unresolved-signature policy. It is for a single demo workspace with Administrator/Auditor permissions; completing this slice does not complete the full MVP or issuer-scoped evidence privacy. Pending wallets and non-eligible investors are not usable for payout. Activation records the original `verifiedAt`; snapshot collection excludes a wallet verified after the effective finalized slot. Revoked and blocked holder balances remain visible to snapshot reconciliation while the current-status eligibility rule prevents new payment to that wallet. Replacement is explicit: revoke the old address, attach the new one, then prove ownership; automatic token transfer is intentionally unsupported. Public Devnet and real-money work are deferred under [ADR-014](../decisions/ADR-014-local-mvp-before-public-network.md).
