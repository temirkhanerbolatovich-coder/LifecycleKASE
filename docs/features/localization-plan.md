# План локализации LifecycleKASE: RU / KK / EN

Первоначальный план проверен **2026-10-11**, до реализации. Базовый HEAD аудита — `eb7a6025cadb45229949a7107f7e0a72c07e1058`; первоначальные наблюдения ниже сохранены как история.

**Обновление после реализации, 2026-10-11:** добавлен RU/EN интерфейс: selector, SSR cookie и metadata, все разделы, финансовые панели, статусы, известные ошибки, точные суммы и даты. Проверены сохранение формы и ошибки при смене языка, reload языка и мобильные ширины 390/320. См. [приёмку кандидата](../testing/submission-readiness-2026-10-11.md) и [ADR-027](../decisions/ADR-027-display-locales.md). KK остаётся планом и черновым глоссарием до языковой проверки. Эта реализация ещё не означает опубликованную English-версию на Render.

## Цель и приоритет

Оператор должен понимать этап, сумму, полномочия, риск повторной отправки и доказательство результата на выбранном языке. Для международной сдачи сначала нужна цельная английская подача; казахская версия должна пройти проверку носителем языка с финансовой терминологией. Срок сдачи нельзя расходовать на миграцию стека или добавление переводческого сервиса.

Основной хакатон Crypto World's Fair требует английский контент: раздел 12(a)(i) [официальных правил](https://colosseum.com/legal/Crypto%20World%27s%20Fair%20Hackathon%20Rules.pdf), проверен 2026-10-11. Существующие английские титры поверх русскоязычного интерфейса нельзя объявлять подтверждённым соответствием этому требованию. Практичный вариант — английские видимые экраны для записи плюс английские сценарий, описание и технический обзор; иной вариант требует разъяснения организатора. Полная KK-локализация не является обнаруженным требованием сдачи.

API и receipt могут содержать пользовательские названия, имена, причины решений и документы. Их нельзя автоматически подменять переводом или отправлять внешнему переводчику. Технические значения и пользовательский контент должны оставаться узнаваемыми.

## Минимальная архитектура

1. Поддерживаемые UI-языки: `ru`, `kk`, `en`; форматы: `ru-KZ`, `kk-KZ`, `en-GB`. Сохранить RU как первоначальную локаль существующего продукта; EN использовать для международной демонстрации. Это предложенный выбор, его надо зафиксировать при реализации.
2. Каталоги одной формы: `common`, `navigation`, `auth`, `actions`, `instruments`, `investors`, `transactions`, `audit`, `system`, `qa`. Ключи описывают смысл (`action.confirmExistingSignature`), а не полный русский текст. Ключи и enum values остаются стабильными.
3. Общий locale context располагается выше `OperatorWorkspace`. Переключение языка меняет текст без remount: не теряются выбранная карточка, unsent form, filters, signed attempt UUID/signature и review state. Предпочтение сохраняется только как локаль, без кошелька/секретов.
4. Первоначальную локаль и `html lang` выдавать согласованно с сервером; допустим небольшой cookie предпочтения. Не читать `localStorage` в серверном render и не создавать hydration mismatch. Переключатель с явными названиями **Қазақша / Русский / English** доступен на входе и в рабочем месте; флаги не использовать как языки.
5. Существующие чистые presentation helpers принимают локаль/переводчик отдельно от доменных данных. State machine, права, API routes, payloads и finalized checks остаются прежними. Не заводить parallel translated workflows.
6. Для сообщений с переменными переводить целое предложение с именованными параметрами. Не собирать предложение из отдельных слов; списки/количество использовать через понятные варианты и `Intl.PluralRules`, когда это требуется текстом.
7. Ключи KK/EN проверяются на полноту относительно RU. Для ещё отсутствующего обычного текста допустим документированный fallback; critical signing/recovery/disclaimer экран должен иметь полный перевод до включения локали. Нельзя выпускать частично переведённый financial confirmation.

Для текущих трёх локалей отдельная зависимость не обязательна. Возвращаться к i18n-библиотеке стоит при реальной потребности в сложных plural/select сообщениях, внешнем переводческом процессе или локализованных URL. Это решение надо оценить по объёму извлечённых строк, а не выбирать инструмент заранее.

## Суммы, время и смысл

- **KZT-Test всегда остаётся KZT-Test.** Не заменять на `₸`, «цифровой тенге» или настоящие KZT. Существующие суммы имеют 6 minor decimals; точность, floor rounding и canonical receipt неизменны. Для локального decimal/group separator форматировать целую и дробную части безопасно; не конвертировать полный minor amount в Number. Copy/raw view сохраняет canonical numeric string.
- В первой версии можно сохранить canonical dot-decimal ввод с явной подсказкой «точка, до 6 знаков». При добавлении RU/KK запятой нужен отдельный строгий parser, который нормализует один допустимый separator в исходный контракт. Отвергать неоднозначные `1,000`/`1.000`, exponent, minus и превышение диапазона; не удалять знаки молча. Native `type=number` поведение проверить в браузерах.
- Показывать `planned record time` и `effective finalized cutoff` раздельно. Смена локали не превращает planned time в юридический исторический cutoff. Для доказательств дополнительно доступен исходный UTC ISO timestamp/slot.
- Часовой пояс выбирается независимо от языка. Казахский или русский интерфейс не означает автоматически UTC+5: оператор может находиться в другом месте. Для записи установить Asia/Qyzylorda либо UTC и явно показать его.
- `UNKNOWN_CONFIRMATION` переводить как **результат неизвестен**, а не **операция не выполнена**. `PREPARED`, `SUBMITTED`, `FINALIZED` и application `APPROVED` не сливать в один «успешно».
- Переводить подсказку о wallet challenge, но не байты challenge/message, которые сервер ожидает подписать. То же относится к exact transaction, Solana addresses, operation IDs, PDAs, receipt JSON/hash и user-entered names. UI-язык не влияет на подпись или финансовую операцию.

## Проверки при реализации

1. RU/KK/EN: вход, семираздельная навигация, таблицы, формы, loading/empty/validation/error, action details, unknown confirmation, reauthentication, receipts и QA-disclosures. Испытать Auditor и обе Administrator роли.
2. Во время заполнения формы и во время review сохранённой попытки переключить язык. Сравнить выбранный UUID, original signature, review object и UTC request payload до/после; не должно появиться нового prepare/submit.
3. Даты по UTC и Asia/Qyzylorda вокруг полуночи; invalid/null date; одинаковые planned/effective timestamps во всех локалях.
4. Суммы `0`, `1` minor unit, `500000000`, `9223372036854775807`: та же точная сумма во всех локалях; fractional precision не исчезает. Сверить скачанный receipt/hash, не только текст экрана.
5. Поиск на кириллице/казахских буквах/Latin, numeric sorting; исходные status codes и IDs тоже находятся. Это поиск по загруженной странице, не новая server search функция.
6. Glyphs и реальные KK предложения, long EN/KK labels, mobile 390 px, keyboard tab order, 200% zoom, aria/live errors. Cmap pass не заменяет визуальную проверку.
7. `npm run test --workspace @lifecycle-kase/web`, web typecheck/build и общий `npm run validate`; сохранить regression проверки recovery/precision и browser evidence. Эти проверки перечислены как будущая приёмка локализации, не заявлены выполненными для новой функции.

## Что было неизвестно при первоначальном аудите

Носитель/редактор KK и финальное подтверждение терминов пока не назначены. Экранного EN-перевода нет. Исходный английский glossary и metadata ещё не утверждены владельцем. В этом аудите проверены исходники, сумма/date helpers и cmap; полноценная browser-приёмка языков возможна после реализации.

После реализации RU/EN проверен в браузере и регрессионных тестах. Открыты KK-перевод и проверка носителем, отдельная приёмка screen reader/200% zoom и ручная проверка смены языка во время реальной wallet recovery. Неизвестные внешние ошибки и пользовательский контент сохраняют исходный язык. Нативный календарь зависит от языка браузера/ОС. Публичный Render deployment требует отдельной проверки.

Связанный [план английского demo и pitch](../submission/ENGLISH_DEMO_AND_PITCH_PLAN.md) отделяет реальную Localnet финансовую запись от QA-симуляции и публичного staging.
