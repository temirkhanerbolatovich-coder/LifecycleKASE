# Solana client boundary

The implemented holder collector reads all positive-balance Token-2022 accounts for one zero-decimal bond mint at `finalized` commitment. It uses `getProgramAccounts` with a mint filter and `withContext`, decodes the 165-byte base account prefix (also valid when extensions follow it), groups token accounts by owner wallet, and reconciles their sum with mint supply. A second step joins wallets to the Investor Registry mapping and identifies unknown or unverified owners. The caller must refuse snapshot creation when `canCreateSnapshot` is false.

The collector brackets the account read with two `getTokenSupply` calls and rejects changed supply or unordered slots. The registry account read has a single reported context slot; this does not prove the RPC provider is honest or that the later snapshot transaction will land in the same slot. The API binds the result to the action window, persists the canonical snapshot, and verifies the on-chain commitment after signing. Disposable live-mint and persistent owner snapshot acceptance are recorded in the [action evidence](../../docs/testing/localnet-action-acceptance.md).

`HttpSolanaRpc` permits HTTPS endpoints and local HTTP only. It rejects redirects, applies a timeout, and does not include endpoint credentials or raw provider error details in its errors. Configure provider URLs server-side; do not place API keys in frontend bundles or logs.

Run `npm test --workspace @lifecycle-kase/solana-client` and `npm run typecheck --workspace @lifecycle-kase/solana-client` from the repository root. The tests use deterministic RPC fixtures. The package includes snapshot registration and all four instrument deployment builders (`MINT_SETUP`, `DISTRIBUTION`, `INITIALIZE`, `ACTIVATE`), Instrument PDA decoding, unsigned v0 transaction construction, and exact finalized-transaction verification. Persistent owner issuance and snapshot happy paths are accepted; funding, payment/redemption and remaining manual variants are separate gates.

The v0 serializer includes explicit `SetComputeUnitLimit` (400,000 CU by default) and `SetComputeUnitPrice` (0 micro-lamports/CU for the demo). Both are part of the persisted message before signing. [Phantom otherwise adds priority instructions at signing time](https://docs.phantom.com/developer-powertools/solana-priority-fees), which changes the message and correctly fails exact-byte verification. Serializer callers may supply a validated compute limit and price; duplicate compute-budget instructions are rejected. Zero priority price is a local demo default, not a public-network inclusion guarantee. A wallet-modified message is never accepted or silently normalized.

The isolated validator suite now submits all four actual application v0 plans, verifies their exact finalized wire messages, mint authorities, 10/20/5 balances and Deploying/Active PDAs. This uses a disposable signer, not Phantom, and does not prove HTTP/PostgreSQL or extension acceptance.

The client also exports entitlement registration/reset/finalization builders and recognizes CALCULATED/UNDER_REVIEW Action PDA statuses. The API/dashboard integration is feature-flagged; owner program upgrade and persistent entitlement acceptance remain pending. See [on-chain calculation candidate](../../docs/features/on-chain-entitlement-registration.md) for authority, coverage and transaction bounds.

## Loader upgrade preparation

`decodeUpgradeableProgram`, `decodeUpgradeableProgramData`, `decodeUpgradeableBuffer` and `deriveUpgradeableProgramData` expose validated loader-v3 metadata. Callers must additionally verify RPC account ownership/executable flags, exact genesis, authority and reviewed ELF/hash/length. `programUpgradeCapacity` enforces account limits and extension minimums. `buildProgramUpgrade` requires an explicit EXTEND or UPGRADE phase and returns one public instruction with only the external authority wallet as signer/fee payer. UPGRADE uses that wallet as spill receiver and refuses insufficient capacity; EXTEND refuses already sufficient capacity. The pinned runtime supports opcode 6 for extension; extension and upgrade must be separately confirmed, with a later finalized slot before UPGRADE. Extension's payer is constrained by the client plan; on-chain upgrade authority is enforced by the subsequent Upgrade instruction.

The builder neither stages a buffer nor signs, broadcasts, stores an attempt or authorizes an upgrade. `npm run localnet:upgrade:preflight` performs the corresponding read-only owner program/artifact/rent checks. See the [reviewed package and pending signing integration](../../docs/deployment/owner-localnet-program-upgrade.md). Disposable exact-v0 loader/runtime acceptance and real Phantom/owner acceptance must remain distinct.
