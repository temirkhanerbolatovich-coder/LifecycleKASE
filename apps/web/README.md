# Web boundary

The Next.js application contains a Russian status dashboard at `/dashboard`, operator wallet login, an administrator snapshot registration panel, and a liveness route at `/health/live`. The home route redirects to the dashboard. It uses the existing mark at `public/brand/lifecyclekase-mark.png`.

The dashboard fetches `GET /api/v1/health/ready` on the server through `API_INTERNAL_URL` (default `http://127.0.0.1:4000`). A failed or timed-out request is shown as unavailable; the page remains renderable. The readiness signal covers the API and PostgreSQL only, not Solana or a working financial flow. No private URL or database credential is sent to the browser.

The client-side login panel discovers compatible wallets through Wallet Standard. It requires `standard:connect` and `solana:signMessage`, tracks `standard:events` account changes when supported, requests the backend's one-time domain-bound challenge, verifies that the wallet signed the exact bytes, and exchanges the signature for an HttpOnly session cookie. When one Phantom profile exposes several accounts, the panel follows the single active account or requires an explicit address when several are exposed; it never silently retains a stale first account. Phantom profile names are not identities. The browser never receives a private key or seed phrase. Operator requests use relative `/api/v1` URLs through fifteen fixed Next.js rewrites to `API_SERVER_URL`, then `API_INTERNAL_URL`, then local `http://127.0.0.1:4000`. The upstream must be an HTTPS origin or local HTTP origin without credentials/path/query/fragment. `NEXT_PUBLIC_API_URL` is no longer used for operator requests. Rebuild when changing the upstream.

The authenticated dashboard exposes audited [instrument drafts and phased deployment](../../docs/features/instrument-drafts.md) plus the first [Investor Registry slice](../../docs/features/investor-registry.md). Administrator creates fixed-supply drafts and can review/sign `MINT_SETUP` through Phantom; finalized confirmation is separate. Administrator/Auditor can read instruments. The UI keeps the instrument in DRAFT and labels distribution/initialization/activation as pending. This fixture evidence is not live Localnet or public Devnet issuance acceptance.

This keeps host-only HttpOnly/SameSite=Strict/Secure-in-production cookies on the web origin even when API and web use different Render sites. The API still validates the exact browser Origin and session role. The web server transports cookies but must not log them. Proxied users can share an API rate-limit bucket behind web egress: this is a single-operator demo limitation, not scalable ingress. See [ADR-012](../../docs/decisions/ADR-012-same-origin-operator-api.md). The UI reports disabled authentication, unauthorized wallets, origin mismatch and expired challenges.

For the disposable Render staging Blueprint, `API_SERVER_URL` overrides that local setting with the API's public HTTPS URL. Free Render web services cannot receive private-network traffic from each other. The dashboard requires the expected JSON response, not just HTTP 200, because a sleeping free API may initially return a platform loading page.

Run `npm run dev:web` at the repository root. For production-style local testing, run `npm run build --workspace @lifecycle-kase/web` and `npm run start:web`. A real login additionally requires `AUTH_ENABLED=true`, exact API CORS/origin configuration, and a pre-provisioned active operator wallet. Broader administrator/auditor workflows and any investor cabinet are pending. Do not treat the roadmap cards as live actions.

## Snapshot registration

After an ADMINISTRATOR login, enter the UUID of an existing SCHEDULED corporate action. The API must be configured for Localnet or Devnet with its exact expected genesis hash and matching `WALLET_NETWORK`; the instrument, program, mint and investor wallet mappings must already exist. The UI does not create those records. The session wallet must also be the instrument's issuer authority.

1. Prepare or refresh an unsigned plan. The API captures/resumes the immutable snapshot, writes a new attempt, and returns its persisted cluster. The browser accepts only Localnet or Devnet, the expected action and signer, and canonical unsigned v0 framing; it also checks the transaction's fee payer. It does not independently decode/attest every instruction or prove RPC correctness.
2. Review the genesis hash, signer, program, Action PDA, snapshot hash, planned date, actual finalized capture slot/time and block-height limit. Acknowledge the review, then explicitly sign/send through `solana:signAndSendTransaction`. The Wallet Standard chain is derived from the validated plan (`solana:localnet` or `solana:devnet`); the wallet and exact account must advertise that chain and v0 support. Preflight is enabled; no private key is sent to the server.
3. Save the action UUID, attempt UUID and signature. Click the separate finalized check. Only an API FINALIZED response matching that attempt and signature is presented as success. The API verifies the exact prepared message, signer and resulting Action PDA. A wallet submission result alone is not confirmation.

There is no automatic resend or confirmation polling. After invoking the wallet, another send is disabled for this mounted panel even if the wallet rejects or its response is lost: the application cannot safely distinguish rejection from a successful send with a lost response. Check wallet history and use the confirmation/recovery inputs, including after a page reload. State is not stored in browser storage; retain the identifiers yourself. Refreshing the page does not prove that a previous send failed. Re-prepare only after establishing that no transaction was submitted, and within the record-date window. Expired blockhash or missed record-date windows must not be bypassed. A wallet that does not advertise the plan's chain is rejected before signing.

DEMO_CAPTURE_SLOT refers to ownership at the effective capture slot, not historical ownership at the earlier planned record date. Localnet uses its disposable local fee asset; Devnet uses test SOL. Registration is not a coupon/payment/burn. The owner accepted local signed operator flows, but no live Localnet snapshot registration or public Devnet end-to-end acceptance has been performed. See the [deployment record](../../docs/deployment/render-staging.md).

Run `npm run test --workspace @lifecycle-kase/web` for network/boundary/encoding/finalization checks. `npm test` also checks compatibility with the actual backend transaction serializer. These tests do not replace wallet-extension and live Localnet or Devnet acceptance.

Follow the [Devnet acceptance checklist](../../docs/testing/devnet-snapshot-acceptance.md) for user-controlled wallet setup, prerequisite gates and required evidence.

`node scripts/test-web-operator-proxy.mjs` builds and runs an isolated production web server against a synthetic local backend. It verifies preserved Origin/body, Strict HttpOnly Set-Cookie, session Cookie forwarding, actual snapshot UUID routing and that unknown routes are not proxied. It is transport evidence only, not a real-wallet session. The smoke build points to its temporary backend; run the normal web build again before manually starting that build for development.
