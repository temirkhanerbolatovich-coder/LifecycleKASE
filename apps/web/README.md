# Web boundary

The authenticated dashboard now includes [corporate action creation/list/detail, wallet-signed scheduling/cancellation and embedded snapshot](../../docs/features/corporate-actions.md). Administrator mutations require the instrument issuer's session wallet; Auditor can read terms, recent transactions and audit. Localnet action/snapshot submission uses Phantom signing plus exact Ed25519-verified API broadcast, matching the accepted instrument custody boundary.

The Next.js application contains a Russian status dashboard at `/dashboard`, operator wallet login, an administrator snapshot registration panel, and a liveness route at `/health/live`. The home route redirects to the dashboard. It uses the existing mark at `public/brand/lifecyclekase-mark.png`.

The dashboard fetches `GET /api/v1/health/ready` on the server through `API_INTERNAL_URL` (default `http://127.0.0.1:4000`). A failed or timed-out request is shown as unavailable; the page remains renderable. The readiness signal covers the API and PostgreSQL only, not Solana or a working financial flow. No private URL or database credential is sent to the browser.

The client-side login panel discovers compatible wallets through Wallet Standard. It requires `standard:connect` and `solana:signMessage`, tracks `standard:events` account changes when supported, requests the backend's one-time domain-bound challenge, verifies that the wallet signed the exact bytes, and exchanges the signature for an HttpOnly session cookie. When one Phantom profile exposes several accounts, the panel follows the single active account or requires an explicit address when several are exposed; it never silently retains a stale first account. Phantom profile names are not identities. The browser never receives a private key or seed phrase. Operator requests use relative `/api/v1` URLs through a fixed Next.js rewrite allowlist to `API_SERVER_URL`, then `API_INTERNAL_URL`, then local `http://127.0.0.1:4000`. The upstream must be an HTTPS origin or local HTTP origin without credentials/path/query/fragment. `NEXT_PUBLIC_API_URL` is no longer used for operator requests. Rebuild when changing the upstream.

The authenticated dashboard exposes audited [instrument drafts and phased deployment](../../docs/features/instrument-drafts.md) plus the first [Investor Registry slice](../../docs/features/investor-registry.md). Administrator creates fixed-supply drafts and can separately review/sign `MINT_SETUP`, 10/20/5 `DISTRIBUTION`, `INITIALIZE` and `ACTIVATE` through Phantom; finalized confirmation is separate for every phase. On Localnet, Phantom signs the exact prepared bytes and the API verifies/broadcasts them through its configured loopback RPC. On Devnet, the wallet remains responsible for submission. Distribution choices are limited to three distinct active verified eligible investor wallets. The UI shows `DRAFT → DEPLOYING → ACTIVE` only after the matching finalized transaction and on-chain read-back. Administrator/Auditor can read instruments. The four-phase live Phantom/Localnet happy path passed for LKA26R1, including same-wallet session recovery. Additional manual negative scenarios remain pending and public Devnet acceptance remains deferred; see the [acceptance record](../../docs/testing/localnet-instrument-acceptance.md).

If a protected request returns `SESSION_REQUIRED` or `SESSION_INVALID`, the dashboard marks the session expired and offers a fresh message-signature login with the same operator wallet. Child workflow panels remain mounted during recovery so their operation UUID and transaction signature are retained. Protected requests are never replayed automatically after login. Repeat only finalized confirmation for an already signed operation. After a full reload, preparing the same pending phase returns its persisted status/signature; a resumed signed attempt disables another transaction signature and exposes confirmation. If restoring DISTRIBUTION, select the original three 10/20/5 investors and prepare again to retrieve the stored attempt. The server's expiry, role, Origin and signature checks remain mandatory; recovery never extends a session without a new wallet proof.

This keeps host-only HttpOnly/SameSite=Strict/Secure-in-production cookies on the web origin even when API and web use different Render sites. The API still validates the exact browser Origin and session role. The web server transports cookies but must not log them. Proxied users can share an API rate-limit bucket behind web egress: this is a single-operator demo limitation, not scalable ingress. See [ADR-012](../../docs/decisions/ADR-012-same-origin-operator-api.md). The UI reports disabled authentication, unauthorized wallets, origin mismatch and expired challenges.

For the disposable Render staging Blueprint, `API_SERVER_URL` overrides that local setting with the API's public HTTPS URL. Free Render web services cannot receive private-network traffic from each other. The dashboard requires the expected JSON response, not just HTTP 200, because a sleeping free API may initially return a platform loading page.

Run `npm run dev:web` at the repository root. For production-style local testing, run `npm run build --workspace @lifecycle-kase/web` and `npm run start:web`. A real login additionally requires `AUTH_ENABLED=true`, exact API CORS/origin configuration, and a pre-provisioned active operator wallet. Broader administrator/auditor workflows and any investor cabinet are pending. Do not treat the roadmap cards as live actions.

## Snapshot registration

After an ADMINISTRATOR login, open a SCHEDULED corporate action to use its embedded snapshot panel. The advanced panel also accepts an existing action UUID. Create and schedule actions through the action workflow above. The API must be configured for Localnet or Devnet with its exact expected genesis hash and matching `WALLET_NETWORK`; the instrument/program/mint and verified investor mappings must already be accepted. The session wallet must also be the instrument's issuer authority.

1. Prepare or refresh an unsigned plan. The API captures/resumes the immutable snapshot, writes a new attempt, and returns its persisted cluster. The browser accepts only Localnet or Devnet, the expected action and signer, and canonical unsigned v0 framing; it also checks the transaction's fee payer. It does not independently decode/attest every instruction or prove RPC correctness.
2. Review the genesis hash, signer, program, Action PDA, snapshot hash, planned date, actual finalized capture slot/time and block-height limit. Acknowledge the review. Localnet uses `solana:signTransaction` followed by exact Ed25519-verified API broadcast; Devnet uses `solana:signAndSendTransaction`. The Wallet Standard chain is derived from the validated plan (`solana:localnet` or `solana:devnet`); the wallet and exact account must advertise that chain and v0 support. Preflight is enabled; no private key is sent to the server.
3. Save the action UUID, attempt UUID and signature. Click the separate finalized check. Only an API FINALIZED response matching that attempt and signature is presented as success. The API verifies the exact prepared message, signer and resulting Action PDA. A wallet submission result alone is not confirmation.

The snapshot finalized button retries only TRANSACTION_NOT_FINALIZED, at most 16 checks spaced three seconds apart; authentication/history/message/rate/transport errors stop immediately. It retains the exact UUID/signature and never resends. After invoking the wallet, another send is disabled for this mounted panel even if the wallet rejects or its response is lost: the application cannot distinguish rejection from a successful send with a lost response. Check history and use confirmation/recovery inputs after reload. The server resumes received signed attempts unchanged even after window/blockhash expiry for confirmation only. State is not stored in browser storage; retain identifiers especially if the server never received signed bytes. New unsigned preparation requires finalized block-height expiry checks and the record window. A wallet that does not advertise the plan's chain is rejected before signing.

DEMO_CAPTURE_SLOT refers to ownership at the effective capture slot, not historical ownership at the earlier planned record date. Localnet uses its local fee asset; Devnet uses test SOL. Registration is not a coupon/payment/burn. Disposable-validator tests and the persistent owner Phantom coupon snapshot happy path passed; remaining manual variants and public Devnet stay pending. See [live evidence](../../docs/testing/localnet-action-acceptance.md) and [deployment record](../../docs/deployment/render-staging.md).

Run `npm run test --workspace @lifecycle-kase/web` for network/boundary/encoding/finalization checks. `npm test` also checks compatibility with the actual backend transaction serializer. These tests do not replace wallet-extension and live Localnet or Devnet acceptance.

Follow the [Devnet acceptance checklist](../../docs/testing/devnet-snapshot-acceptance.md) for user-controlled wallet setup, prerequisite gates and required evidence.

`npm run test:web:proxy` builds and runs an isolated production web server against a synthetic local backend. It verifies preserved Origin/body, Strict HttpOnly Set-Cookie, session Cookie forwarding, snapshot/action UUID routing, registry/deployment, three entitlement and four coupon budget/funding routes, plus unknown-route isolation across 30 allowlisted routes. CI runs this transport check. It is transport evidence only, not a real-wallet session. The smoke build points to its temporary backend; run the normal web build again before manually starting that build. Production `.next` and dev output are separate; avoid concurrent production builds.

## Entitlements and review

For a selected action with a FINALIZED snapshot, **Начисления и согласование** shows receiver choices, stored investor amounts/balances/redemption counts, formula inputs/version/remainder and current eligibility. Administrator issuer wallet can calculate, submit, explicitly approve/reject/return with a comment; Auditor reads. Review requires an explicit acknowledgement. Revision uses the same immutable snapshot and entitlement IDs. Values retain six-decimal bigint precision; lost responses require refresh without automatic mutation replay. Application APPROVED does not execute a payment or change the retained Action PDA. See [feature and limits](../../docs/features/entitlements-and-review.md).

When the guarded server capability is enabled, the same panel lets the corporate action authority register each stored entitlement, reset a confirmed partial set, and finalize the full on-chain calculation. Before Phantom opens, the browser verifies the selected action/version, CA signer, snapshot hash, exact ordered PDA set, amount/count/total and the unsigned v0 fee payer. A saved signature restores confirmation without another signing prompt. RESET preserves the snapshot and is unavailable after finalization. Approval remains disabled until CALCULATION_FINALIZE is finalized. See [on-chain registration](../../docs/features/on-chain-entitlement-registration.md).

## Coupon budget and funding

For a selected coupon UNDER_REVIEW or application APPROVED, **Бюджет и финансирование купона · Localnet** automatically reads whole-coupon/treasury/deficit/SOL facts and restores any saved plan. The issuer Administrator reviews mint, treasury, network and amount, then signs exact funding bytes through Phantom. Unsigned blockhashes refresh immediately before signing; changed amounts require review again. Signed attempts resume confirmation without another wallet invocation. Auditor reads budget only. Finalization checks the exact transaction token delta and current treasury; it does not approve or pay the coupon. Isolated real-validator funding passed; owner Phantom funding and separate Auditor presentation remain pending. See [feature and recovery](../../docs/features/coupon-funding.md).
