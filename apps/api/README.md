# API boundary

[Corporate actions](../../docs/features/corporate-actions.md) expose audited idempotent draft creation, bounded list/detail, untouched-draft cancellation, and separate wallet-signed SCHEDULE/CANCEL prepare/submit/confirm routes. All three action types validate dates and redemption terms. Snapshot persists exact unsigned wire and resumes the signed attempt for confirmation. Apply the action-operation migration; `npm run test:actions:database` verifies this boundary and stored calculation/review in a generated disposable database.

[Stored entitlements/review](../../docs/features/entitlements-and-review.md) adds GET `/:id/entitlements`, POST `/:id/entitlements/calculate` (`version`, optional verified `receivers`) and POST `/:id/entitlements/review` (`version`, explicit SUBMIT/APPROVE/RETURN/REJECT, `note`) under `/api/v1/corporate-actions`. Administrator issuer-session writes and Auditor reads, Origin/rate limits, reconstructed snapshot integrity, Serializable versions and atomic audit apply. Calculations aggregate investor wallets/accounts and store bigint inputs/formula/rule versions; approval and the future execution gate check current eligibility and receiver facts. No schema migration, payment, burn or on-chain approval is added. The feature documents narrowly scoped authorized Localnet CLI confirmation/preparation; it stops at UNDER_REVIEW and leaves HTTP authentication intact.

[On-chain entitlement registration](../../docs/features/on-chain-entitlement-registration.md) adds guarded `/:id/entitlements/onchain/prepare`, `/submit` and `/confirm` routes for REGISTER/FINALIZE/RESET. `ONCHAIN_ENTITLEMENT_REGISTRATION_ENABLED` defaults to false and Localnet is required. Corporate action authority, genesis, program, finalized snapshot, stored calculation, Action/Entitlement PDA contents, counters and integer totals are checked through exact finalized read-back. RESET closes only the full confirmed partial set before UNDER_REVIEW and atomically clears database PDA projections after chain evidence. Enabling the capability also blocks application approval until CALCULATION_FINALIZE is finalized. The retained owner program has not been upgraded; keep the flag false there until a reviewed upgrade.

[Coupon budget/funding](../../docs/features/coupon-funding.md) adds GET `/:id/coupon/budget` and POST `/:id/coupon/funding/prepare`, `/submit`, `/confirm`. Budget covers the full stored coupon and a configured policy SOL reserve; preparation accepts only `{version}` and derives the exact treasury deficit. Wallet-signed Localnet funding uses retained issuer mint authority, exact signed-wire verification and finalized treasury token-delta evidence. Audit commits atomically and no action approval/payment is performed. Apply migration 18, `20261003001000_coupon_funding_operations`; one unresolved funding attempt per issuer is database-enforced. Controlled Localnet CLI can prepare unsigned funding or confirm an already audited signed attempt without keys, broadcast or browser sessions.

Localnet instrument `POST /api/v1/instruments/:id/deploy/submit` accepts only an Administrator session, exact allowed Origin, the matching issuer signer, a supported phase/operation, and the exact persisted transaction with a valid Ed25519 signature. It broadcasts through the configured RPC and retains unknown-response recovery; it never handles private keys. Devnet rejects this route and remains wallet-submitted. Prepared transactions include an explicit compute limit and zero demo priority price before signature; confirmation still compares the entire message. MINT_SETUP verifies absent bond mint/freeze authorities, the permanent delegate, supply/treasury, and retained **issuer** KZT-Test mint authority with no freeze authority. Retained KZT-Test authority supports the separately reviewed Localnet funding flow; investor payments remain unimplemented.

Instrument confirmation distinguishes a pending signature (`TRANSACTION_NOT_FINALIZED`) from a finalized signature with unavailable bytes (`TRANSACTION_HISTORY_UNAVAILABLE`) and an absent signature whose blockhash is no longer valid (`TRANSACTION_UNAVAILABLE`). The latter is ambiguous: a short Localnet ledger may already have discarded a successful transaction. All three remain `UNKNOWN_CONFIRMATION`, preserve the stored signature, and leave projections untouched. A recorded unavailable-history attempt cannot be replaced by `deploy/prepare`; reconcile the RPC history and accounts first. The persistent acceptance validator must use an explicit larger `--limit-ledger-size` and restart its existing ledger without `--reset`; see the [acceptance runbook](../../docs/testing/localnet-instrument-acceptance.md).

Resumed deployment prepare responses include the persisted `status` and `signature` for every phase. An observed signed attempt is returned unchanged even after its blockhash expires; the browser resumes confirmation, not submission. This supports full-reload recovery after session expiry while retaining the same UUID, exact message and signature. Reauthentication still requires the ordinary one-time wallet message proof; it does not bypass the protected confirm route.

The internal `prepareSnapshotCandidate` reads a scheduled corporate action and Investor Registry wallet mappings through Prisma, checks the record-date grace window and expected Solana genesis hash, collects finalized Token-2022 holders, and produces canonical `snapshot-v2` bytes and SHA-256. It refuses unknown wallets, wallets verified after the effective finalized slot, a stale instrument supply projection, unavailable slot block time, a slot before the planned `record_at` or after capture, and an inactive action or instrument. A wallet verified after `record_at` but before the effective slot can enter the demo snapshot. A blocked but verified wallet remains in the ownership snapshot; payout eligibility is a separate decision.

`persistSnapshotCandidate` writes the canonical payload, investor/wallet/token-account rows, and a non-identifying `SNAPSHOT_CAPTURED` audit event in one serializable PostgreSQL transaction. It checks action and instrument versions, current wallet mappings and statuses (including verification by the effective slot), the record-date window, and the candidate hash; a compare-and-set increments the action version. The action stays `SCHEDULED` and the snapshot stays `PENDING_REGISTRATION` until a later signed on-chain registration is confirmed. A retry must resume that pending snapshot, not recapture holdings for the same action.

`preparePendingSnapshotRegistration` reads that pending snapshot instead of recapturing holders. It reconstructs the canonical `snapshot-v2` hash, verifies persisted counts and fields, checks the configured and RPC genesis hash, finalized capture slot and block time, then returns the exact Anchor instruction accounts/data, issuer signer, and a recent finalized blockhash with expiry. The HTTP orchestration serializes a Solana v0 transaction with an empty issuer signature and records the blockhash-bound attempt as `BlockchainTransaction(PREPARED)`.

`POST /api/v1/corporate-actions/:id/snapshot/prepare` requires an enabled wallet session, exact allowed Origin, and `ADMINISTRATOR` role. It captures and atomically persists a new snapshot or resumes an existing `PENDING_REGISTRATION` snapshot, then returns `operationId`, persisted snapshot `cluster`, planned `recordAt`, effective slot/time, required signer, the checked instruction plan, blockhash expiry, and a base64 Solana v0 wire transaction with an empty issuer signature. It never signs or submits the transaction, and a retry never recaptures balances. Configure `SOLANA_CLUSTER` (`localnet` or `devnet` only), `SOLANA_GENESIS_HASH`, `SOLANA_RPC_URL`, `WALLET_NETWORK`, `SNAPSHOT_GRACE_SECONDS` (maximum 300) and optional `SOLANA_RPC_TIMEOUT_MS`. `WALLET_NETWORK` must be `SOLANA_LOCALNET` for Localnet or `SOLANA_DEVNET` for Devnet; a persisted snapshot from another cluster is rejected before an attempt is written.

`POST /api/v1/corporate-actions/:id/snapshot/confirm` accepts `{ "operationId": "uuid", "signature": "base58" }` under the same authentication, Origin, and role checks. It loads that prepared attempt, verifies the configured/RPC genesis hash, fetches the signature at `finalized`, compares the complete signed message with the blockhash-bound prepared message, checks the issuer signer and successful transaction result, then reads the Action PDA at or after the transaction slot. Only an owner/program match plus exact action ID, instrument PDA, snapshot hash, slot, counts, balance and `SnapshotCreated` state can atomically finalize the transaction attempt, snapshot, action projection and audit event. A temporarily absent finalized transaction becomes `UNKNOWN_CONFIRMATION`; a failed on-chain transaction becomes `FAILED`. For Localnet, the authenticated `/snapshot/submit` boundary verifies the exact persisted wire, signer and Ed25519 signature before broadcast; Devnet submission remains wallet-owned. Historical wallet status changes inside the snapshot window are not fully reconstructible from the current Wallet row; operational controls must freeze or audit registry changes around record dates.

Operator authentication is available at `POST /api/v1/auth/challenge`, `POST /api/v1/auth/verify`, `GET /api/v1/auth/session`, and `POST /api/v1/auth/logout`. A challenge is issued only for an active, verified wallet linked to a non-investor operator role. The wallet signs an Ed25519 message bound to the configured domain, exact browser origin, address, challenge UUID, random nonce, and expiry. Only SHA-256 hashes of the nonce and session token are stored. Verification atomically consumes the challenge and returns a short-lived Secure/HttpOnly/SameSite cookie; no private key is handled by the API. Authentication is disabled unless `AUTH_ENABLED=true`.

Challenge, verification, and protected mutation endpoints use separate fixed-window limits keyed by Express's trusted client address. Configure `AUTH_CHALLENGE_RATE_LIMIT` (default `5`), `AUTH_VERIFY_RATE_LIMIT` (default `10`), `MUTATION_RATE_LIMIT` (default `20`), `AUTH_RATE_LIMIT_WINDOW_SECONDS` (default `60`) and `AUTH_RATE_LIMIT_MAX_CLIENTS` (default `10000`). A rejected request returns HTTP 429, `AUTH_RATE_LIMITED`, and `Retry-After`. The in-memory limiter is appropriate for the single-instance demo; a multi-instance or production deployment needs a shared ingress/distributed limiter. `TRUST_PROXY_HOPS` defaults to `0`; set it only to the reviewed proxy count (`1` in the current Render Blueprint) so clients cannot choose their rate-limit identity through a spoofed forwarding header.

Provision the first operator only through the reviewed [`operator:provision`](../../docs/operations/operator-provisioning.md) command. It accepts a public Solana address, never a private key, rejects investor roles and conflicting existing records, creates an audit event, and is idempotent only for an exact active mapping.

The NestJS HTTP entry point also exposes `GET /api/v1/health/live` (process liveness) and `GET /api/v1/health/ready` (PostgreSQL `SELECT 1`). Readiness returns HTTP 503 with `DATABASE_UNAVAILABLE` on connection failure and does not test Solana RPC or readiness of the snapshot workflow. Set `DATABASE_URL` and optionally `PORT` (default 4000); after `npm run build --workspace @lifecycle-kase/api`, run `npm run start:api`.

The first [Investor Registry slice](../../docs/features/investor-registry.md) adds Administrator/Auditor listing and controlled investor/wallet lifecycle. The [instrument slice](../../docs/features/instrument-drafts.md) adds audited drafts plus Administrator-only `deploy/prepare` and `deploy/confirm` for separate `MINT_SETUP`, `DISTRIBUTION`, `INITIALIZE` and `ACTIVATE` phases. The API persists each exact unsigned transaction and changes projections only after finalized transaction and account reconciliation. Distribution requires three distinct active verified eligible investor wallets and stores their 10/20/5 allocation in `prepared_payload`. Initialization reads back the exact program-owned Instrument PDA before setting `DEPLOYING`; activation repeats current registry eligibility and holder-balance checks, then requires an exact `Active` PDA before setting `ACTIVE`. Apply migrations through `20261003001000_coupon_funding_operations` before local use. All four live Phantom/Localnet issuance phases passed for LKA26R1 with matching Instrument PDA/database state and 10/20/5 balances. Additional manual negative scenarios remain separate gates; see the [acceptance record](../../docs/testing/localnet-instrument-acceptance.md). Public Devnet work is deferred under [ADR-014](../../docs/decisions/ADR-014-local-mvp-before-public-network.md).

For a local-only API, set `API_LISTEN_HOST=127.0.0.1`. When unset it remains `0.0.0.0` for existing hosted services. Accepted values are `127.0.0.1`, `localhost`, `::1`, `0.0.0.0` and `::`.

Run `npm test --workspace @lifecycle-kase/api` for fixture tests. With local PostgreSQL, `npm run test:api:database` checks real snapshot/audit persistence using only isolated records; `npm run test:actions:database` covers action/entitlement/review HTTP and rollback in a disposable DB. The [web wallet flow](../web/README.md) supports Localnet/Devnet submission/recovery; persistent Phantom issuance and coupon snapshot happy paths passed. Payment/redemption and public Devnet acceptance remain pending. Administrator keys must never be stored in this service.
