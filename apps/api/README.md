# API boundary

The internal `prepareSnapshotCandidate` reads a scheduled corporate action and Investor Registry wallet mappings through Prisma, checks the record-date grace window and expected Solana genesis hash, collects finalized Token-2022 holders, and produces canonical `snapshot-v2` bytes and SHA-256. It refuses unknown wallets, wallets verified after the effective finalized slot, a stale instrument supply projection, unavailable slot block time, a slot before the planned `record_at` or after capture, and an inactive action or instrument. A wallet verified after `record_at` but before the effective slot can enter the demo snapshot. A blocked but verified wallet remains in the ownership snapshot; payout eligibility is a separate decision.

`persistSnapshotCandidate` writes the canonical payload and investor/wallet/token-account rows in one serializable PostgreSQL transaction. It checks action and instrument versions, current wallet mappings and statuses (including verification by the effective slot), the record-date window, and the candidate hash; a compare-and-set increments the action version. The action stays `SCHEDULED` and the snapshot stays `PENDING_REGISTRATION` until a later signed on-chain registration is confirmed. A retry must resume that pending snapshot, not recapture holdings for the same action.

`preparePendingSnapshotRegistration` reads that pending snapshot instead of recapturing holders. It reconstructs the canonical `snapshot-v2` hash, verifies persisted counts and fields, checks the configured and RPC genesis hash, finalized capture slot and block time, then returns the exact Anchor instruction accounts/data, issuer signer, and a recent finalized blockhash with expiry. It does not sign, serialize a full transaction, submit, confirm, or update database status. The caller must assemble and have the issuer wallet sign the transaction; a future authenticated confirmation service must verify the finalized transaction and action PDA before changing `PENDING_REGISTRATION` to `FINALIZED`.

These are internal functions, not public HTTP endpoints. They do not authenticate an actor, prepare a serialized wallet transaction, register an on-chain commitment, or claim an operational corporate-action flow. A future endpoint must enforce administrator authorization and audit the write before exposing them. Callers must provide a trusted current time, configured network/genesis hash, wallet network, and `SNAPSHOT_GRACE_SECONDS` (demo default and maximum: 300). Historical wallet status changes inside the snapshot window are not fully reconstructible from the current Wallet row; operational controls must freeze or audit registry changes around record dates.

The NestJS HTTP entry point currently exposes only `GET /api/v1/health/live` (process liveness) and `GET /api/v1/health/ready` (PostgreSQL `SELECT 1`). Readiness returns HTTP 503 with `DATABASE_UNAVAILABLE` on connection failure and does not test Solana RPC or readiness of any corporate-action workflow. Set `DATABASE_URL` and optionally `PORT` (default 4000); after `npm run build --workspace @lifecycle-kase/api`, run `npm run start:api`. Do not publicly expose any domain route before authentication, authorization, and audit controls exist.

Run `npm test --workspace @lifecycle-kase/api` from the repository root for fixture tests. With local PostgreSQL running and migrations applied, run `npm run test:api:database` for a real Prisma write/read/duplicate check; the script creates only isolated test records and removes them afterwards. A live mint and authenticated HTTP API are still pending. Administrator keys must never be stored in this service.
